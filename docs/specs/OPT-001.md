# OPT-001/BENCH-001: Otimização de inferência via ONNX + benchmark

Spec enxuta (sprint final) — cobre os dois requisitos juntos: aplicar uma técnica de otimização
de latência (OPT-001, requisito oficial cita ONNX como exemplo) e comparar com o original
(BENCH-001).

## Objetivo

Converter o baseline (ML-003) para ONNX, validar que o resultado é correto (mesmas classes e
probabilidades do sklearn original, com tolerância), e medir a latência real dos dois lado a
lado.

## Abordagem tentada, em ordem

1. **Pipeline inteiro** (`TfidfVectorizer` + `LogisticRegression`) convertido de uma vez via
   `skl2onnx.convert_sklearn`, input `StringTensorType`. **Funcionou de primeira** — o
   `TfidfVectorizer` foi treinado com todos os hiperparâmetros default (`ngram_range=(1,1)`, sem
   `stop_words` customizado — ver `notebooks/02_baseline.ipynb`/`airflow/dags/`), exatamente o
   caso mais simples de converter; não foi preciso o fallback.
2. Fallback (classificador isolado, TF-IDF em sklearn) implementado no script mas **não usado**
   nesta execução — fica pronto no código (`convert_classifier_only`) caso o retreino futuro
   mude os hiperparâmetros do `TfidfVectorizer` para algo que o `skl2onnx` não converta.

## Resultado

**Abordagem que funcionou: pipeline inteiro em ONNX.**

### Corretude (150 textos reais do dataset, amostrados de `data/raw/fedmml_ed_triage_raw.parquet`)

| | |
|---|---|
| Classes previstas batendo | 150/150 (100%) |
| Diferença máxima de probabilidade | `8.11e-08` |
| Dentro da tolerância (`atol=1e-4`) | Sim |

### Latência (300 iterações cada, mesma entrada fixa, mesma máquina, após 10 iterações de warmup)

| | sklearn original | ONNX (onnxruntime) |
|---|---|---|
| Média | 0.427 ms | 0.040 ms |
| Mediana | 0.403 ms | 0.036 ms |
| p95 | 0.550 ms | 0.050 ms |

**Speedup: ~11x na mediana, ~11x no p95.**

### Tamanho do artefato

| | `.joblib` (sklearn) | `.onnx` |
|---|---|---|
| Tamanho | 9.044 bytes | 7.076 bytes (-22%) |

Números completos (3 execuções independentes, todas na mesma ordem de grandeza — 10.9x/11.7x,
11.5x/13.0x, 11.1x/11.1x) em
[docs/experiments/OPT-001-benchmark.json](../experiments/OPT-001-benchmark.json) (última run).

## Interface

`benchmarks/opt001_onnx_benchmark.py` (`uv sync --extra benchmark --extra data` +
`uv run python benchmarks/opt001_onnx_benchmark.py`):
1. Carrega `models/tfidf_logreg_baseline.joblib`
2. Tenta converter o pipeline inteiro; se corretude não bater, cai pro fallback (classificador
   isolado) — se nem o fallback bater corretude, o script falha ruidosamente (não segue pra
   latência com resultado errado)
3. Mede latência dos dois lados, salva `docs/experiments/OPT-001-benchmark.json`
4. Salva o `.onnx` resultante em `models/` (`tfidf_logreg_baseline.onnx` — não versionado,
   mesmo tratamento do `.joblib`)

## Riscos

- `.onnx` não versionado (mesmo tratamento do `.joblib`, gitignored) — quem quiser reproduzir
  roda o script, que gera a partir do `.joblib` já existente.
- Latência de 0.4ms no sklearn já é extremamente baixa em termos absolutos (a API real tem
  overhead de rede/HTTP/serialização muito maior que isso — ver `LATENCY_BUCKETS_SECONDS` da
  OBS-001, onde a latência ponta-a-ponta observada foi ~6-9ms). O ganho de ~11x é real na
  camada de inferência pura, mas não necessariamente visível como 11x na latência percebida
  pelo cliente da API, dominada por outros fatores. Não medido neste card (fora de escopo:
  trocar o `/predict` pra ONNX).
