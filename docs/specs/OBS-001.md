# OBS-001: Observabilidade da API (Prometheus + Grafana)

## Problema

A API de inferência (API-001, dockerizada na DOCK-001, com CI na CI-001) roda hoje sem nenhuma
visibilidade operacional: não há como saber, sem entrar no container, se a taxa de requisições
está normal, se a latência degradou, se a proporção de erros subiu, ou se a distribuição das
classes previstas mudou. Esse último ponto é especialmente importante num sistema de ML em
produção: **não temos o rótulo verdadeiro** (o desfecho clínico real do paciente) disponível em
tempo real, então não dá para medir acurácia online. Precisamos de um proxy observável que sirva
de sinal de alerta indireto de drift, sem depender do rótulo.

## Objetivo

Instrumentar a API com métricas Prometheus — técnicas (RED: Rate, Errors, Duration) e de negócio
específicas do modelo — e visualizá-las num dashboard Grafana, provisionado junto com
`docker-compose up`, sem passos manuais de configuração pela UI.

## Escopo

1. Métricas RED automáticas via `prometheus-fastapi-instrumentator` (rate, errors, duration por
   rota/método/status) — **este documento cobre a implementação deste passo**.
2. Métricas de negócio customizadas via `prometheus_client` no `POST /predict`: contador de
   predições por classe e histograma da probabilidade da classe prevista (proxy de confiança/drift).
3. `docker-compose.yml` unindo API, Prometheus e Grafana na mesma rede.
4. `monitoring/prometheus/prometheus.yml` com scrape configurado para a API.
5. Provisionamento do Grafana (datasource do Prometheus + dashboard inicial, sem clique manual):
   4 painéis — taxa de requisições, latência p95, distribuição de classes previstas ao longo do
   tempo, histograma de confiança.

**Importante sobre o ritmo de implementação**: os 5 passos acima são implementados e validados
**um de cada vez**, com parada explícita para revisão antes de avançar para o próximo — não é uma
liberação para implementar tudo de uma vez só porque está todo especificado aqui. Este documento
descreve o objetivo final do card; a ordem de execução e os checkpoints são o que efetivamente
acontece sessão a sessão.

## Fora de escopo

- **Alerting via Alertmanager** — decisão explícita do card; fica para uma iteração futura de
  observabilidade se o projeto evoluir para isso.
- **Detecção estatística formal de drift** (teste KS, PSI, etc. comparando a distribuição em
  produção com a distribuição de treino). O que este card entrega é um **proxy visual bruto**
  (contagem por classe + histograma de confiança ao longo do tempo) — útil para um humano notar
  "algo mudou" olhando o dashboard, não um teste estatístico automatizado com p-valor.
- **Autenticação/hardening** do `/metrics` ou do Grafana (fica com usuário/senha padrão,
  `admin/admin` ou equivalente) — aceitável para um ambiente de laboratório rodando localmente;
  precisaria ser revisto antes de qualquer exposição pública (EPIC 12, se chegar lá).
- **Tracing distribuído** (OpenTelemetry, Jaeger, etc.) — fora do que o card pede (métricas, não
  traces).
- **Retenção/armazenamento de longo prazo** do Prometheus (remote write, Thanos, Mimir) — usa a
  retenção local padrão do container.

## Requisitos funcionais

- RF1: `GET /metrics` expõe métricas no formato de exposição do Prometheus (texto plano,
  `# HELP`/`# TYPE` + séries).
- RF2: as métricas RED cobrem, no mínimo: contagem de requisições (rate), status agrupado por
  família (errors: 2xx/4xx/5xx) e duração da requisição (histograma, para permitir p50/p95/p99
  via `histogram_quantile` no Prometheus).
- RF3 *(passo 2)*: contador de predições por classe prevista (`normal`/`atencao`/`urgente`).
- RF4 *(passo 2)*: histograma da probabilidade (confiança) da classe prevista em cada chamada a
  `/predict`.
- RF5 *(passo 3)*: `docker-compose up` sobe os três serviços (API, Prometheus, Grafana) na mesma
  rede Docker, cada um alcançando os outros pelo nome do serviço.
- RF6 *(passo 4)*: o Prometheus faz scrape periódico de `GET /metrics` da API; o alvo aparece
  `UP` em `/targets`.
- RF7 *(passo 5)*: o Grafana já sobe com o datasource do Prometheus e o dashboard de 4 painéis
  provisionados via arquivo — sem precisar criar nada manualmente pela UI.

## Requisitos não funcionais

- RNF1: instrumentação não deve adicionar latência perceptível ao `/predict` — a
  contabilização de métricas é O(1) por requisição (incrementar contador, observar histograma),
  não deve envolver I/O bloqueante.
- RNF2: **nenhum label de alta cardinalidade**. Labels aceitáveis: rota (template, não path bruto
  com query string), método HTTP, status (agrupado), classe prevista (3 valores fixos). Nunca usar
  texto livre (`clinical_notes`) ou qualquer valor de cardinalidade não-limitada como label —
  isso explodiria a quantidade de séries temporais no Prometheus.
- RNF3: o scrape do próprio `/metrics` pelo Prometheus não deve poluir as métricas RED da própria
  API (evitar que "chamadas ao `/metrics`" apareçam como tráfego de negócio).
- RNF4: métricas técnicas e de negócio compartilham o mesmo registry padrão do `prometheus_client`
  — sem múltiplos registries nem duplicação de definição de métrica.
- RNF5: buckets do histograma de latência calibrados para a ordem de grandeza esperada de um
  modelo linear leve (TF-IDF + LogisticRegression) — sub-segundo, não os buckets padrão de
  bibliotecas genéricas (pensados para latência web geral, 100ms–10s).

## Interface esperada — Passo 1 (este documento cobre a implementação)

```python
from prometheus_fastapi_instrumentator import Instrumentator

app = FastAPI(title="Clinical Triage API", lifespan=lifespan)

Instrumentator(
    excluded_handlers=["/metrics"],
    should_group_status_codes=True,
).instrument(app).expose(app, endpoint="/metrics")
```

- `excluded_handlers=["/metrics"]` — RNF3: o próprio scrape não vira uma linha de métrica.
- Buckets de latência customizados (RNF5) — valor exato definido durante a implementação e
  confirmado rodando a API de verdade, não estimado a priori.
- Nomes reais das métricas expostas (`http_request_duration_seconds`, etc. — a confirmar contra a
  versão instalada da lib) documentados no card do KANBAN após validação manual via
  `curl /metrics`, não assumidos de memória.

Passos 2–5 (métricas de negócio, compose, prometheus.yml, provisionamento do Grafana) terão sua
própria interface detalhada quando forem implementados.

## Fluxo de dados

```
Cliente → API (rota normal, ex: POST /predict)
         → middleware do Instrumentator mede duração + status da resposta
         → atualiza contador/histograma no registry do prometheus_client
Prometheus → GET /metrics (scrape periódico, intervalo definido no passo 4)
Grafana    → consulta o Prometheus via PromQL para os painéis do dashboard (passo 5)
```

## Critérios de aceite

- `docker-compose up` sobe os três serviços (API, Prometheus, Grafana) sem erro.
- O Prometheus coleta as métricas da API (alvo `UP`).
- O dashboard do Grafana mostra os 4 painéis com dados reais após chamadas reais a `/predict`
  (sem número inventado — validado rodando de verdade, como em todo o resto do projeto).
- **Critério deste passo (1)**: `GET /metrics` responde `200` com métricas RED reais depois de ao
  menos uma requisição anterior à API; validado por teste automatizado e por `curl` manual.

## Estratégia de testes

- **Passo 1** (`tests/test_api.py`): teste novo confirmando que `GET /metrics` responde `200` e
  que o corpo contém as métricas RED esperadas depois de pelo menos uma requisição prévia a uma
  rota instrumentada. Mesma fixture de modelo sintético já usada nos outros testes da API-001.
- **Passo 2**: teste automatizado dos contadores/histogramas de negócio (contagem por classe
  bate com as chamadas feitas no teste; probabilidade observada aparece no histograma).
- **Passos 3–5**: sem teste automatizado — é infraestrutura (compose, config do Prometheus,
  provisionamento do Grafana), não código Python testável por `pytest`, mesmo raciocínio já
  aplicado no CI-001 para o `Dockerfile`. Validação manual, documentada com evidência real
  (comandos + output, não descrição do que "deveria" acontecer).

## Métricas

Não aplicável no sentido de "métrica de avaliação de um experimento de ML" — este card *é* sobre
expor métricas operacionais, cobertas pelos Critérios de aceite acima.

## Riscos

- **`/health` como ruído na métrica de "taxa de requisições"**: o `HEALTHCHECK` do Docker
  (DOCK-001) bate em `GET /health` a cada 30s, indefinidamente. Sem tratamento, isso vira a
  maior parte do volume de requisições contado nas métricas RED, diluindo o sinal de tráfego real
  do painel "taxa de requisições" (passo 5). Decisão tomada para o Passo 1 (default razoável,
  reversível em uma linha): **excluir `/health` da instrumentação** via `excluded_handlers`, junto
  com `/metrics` — tratando o heartbeat de infraestrutura como não sendo "tráfego de negócio".
  Se a leitura for outra (por exemplo, querer ver o heartbeat como prova de disponibilidade no
  próprio dashboard), é uma reversão trivial.
- **Cardinalidade**: o contador de predições por classe (passo 2) é seguro — 3 valores fixos.
  Risco real seria adicionar no futuro um label de alta cardinalidade (texto do laudo, IDs, etc.)
  — não fazer isso, documentado como RNF2.
- **Histograma de confiança como proxy de drift é uma aproximação**: uma mudança na distribuição
  de confiança pode indicar drift real, mas também pode só refletir uma mudança na mistura de
  casos fáceis/difíceis que chegam à API. Não é um teste estatístico formal — é um sinal visual
  para investigação humana, não uma detecção automática.
- **Sem autenticação no `/metrics` nem no Grafana**: aceitável rodando só localmente via
  `docker-compose`; não deve ser exposto publicamente sem revisão (nota para EPIC 12, se chegar
  lá).
