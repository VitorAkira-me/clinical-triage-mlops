# AIR-001: DAG de treino do baseline (Airflow)

Spec enxuta — requisito oficial é mais simples que o roadmap original previa (sem retreino
agendado, sem sensores): só uma DAG funcional com 2 tasks, rodando de ponta a ponta uma vez.

## Problema

O treino do baseline (ML-003) hoje só existe como notebook rodado manualmente. O requisito oficial
do Tech Challenge (15% da nota) pede orquestração via Airflow — não pede produção contínua.

## Objetivo

Uma DAG com 2 tasks (carregar dataset → treinar e salvar o `.joblib`) que roda com sucesso pelo
menos uma vez.

## Escopo

- DAG `air001_train_baseline` (`airflow/dags/air001_train_baseline.py`), TaskFlow API (Airflow
  2.x): `load_dataset() -> train_baseline()`
- Ambiente: Docker (não Airflow nativo — ver "Decisão: ambiente" abaixo)
- Validação real via `airflow dags test` (CLI, sem precisar da UI/webserver rodando)

## Fora de escopo

- Retreino agendado (`schedule=None`, sob demanda)
- Sensores, retries sofisticados, alerting, particionamento
- Integração com o `docker-compose.yml` do OBS-001 (container Airflow separado, standalone —
  menor blast radius, não arrisca a stack já validada/mergeada)
- Recalcular/sobrescrever `docs/experiments/ML-003-baseline-metrics.json` — a DAG só treina e
  salva o artefato, não recomputa métricas (isso já está feito e documentado na ML-003)

## Decisão: ambiente (Docker, não standalone nativo)

Testado empiricamente antes de decidir: `apache-airflow` instala via pip no Windows nativo, mas
avisa (`RuntimeWarning` no próprio `import airflow`) que só é testado em Linux/macOS, e uma
importação básica (`from airflow.models import DagBag`) já quebra (`ImportError`). Rodar nativo
neste ambiente seria o caminho de **maior** risco pro prazo, não menor. Decisão: container Docker
único com a imagem oficial `apache/airflow:2.10.5-python3.12` (2.x — TaskFlow API mais estável e
documentada que a 3.x, que é onde o erro acima apareceu) + `pip install` das libs de ML por cima
(`airflow/Dockerfile`). Repo inteiro montado em `/opt/airflow/project`; `AIRFLOW__CORE__DAGS_FOLDER`
aponta pra `airflow/dags/` dentro desse mount — sem duplicar arquivo.

## Decisão: origem do CSV

Ordem de fallback na task `load_dataset` (menor esforço/risco primeiro):
1. `data/raw/fedmml_ed_triage_raw.parquet` já existe neste checkout (gerado na OBS-001 Passo 5) →
   reusa direto, sem tocar em rede nem no Hugging Face.
2. Se não existir: `hf_hub_download(..., local_files_only=True)` — usa o cache local do HF (também
   já populado na OBS-001 Passo 5) sem rede nem token.
3. Só se nem 1 nem 2 existirem: baixa de verdade, usando `HF_TOKEN` do `.env` (mesmo mecanismo dos
   notebooks) — caminho mais lento, evitado por design quando possível.

## Critério de aceite

- `airflow dags test air001_train_baseline <data>` roda as 2 tasks com sucesso (sem exceção) ✅
- `models/tfidf_logreg_baseline.joblib` existe no host depois da run (volume montado, não preso
  dentro do container) ✅

**Dois problemas reais encontrados e corrigidos durante a validação** (não hipotéticos):
1. Git-Bash no Windows traduz automaticamente argumentos tipo `/opt/airflow` para caminho Windows
   antes de passar pro `docker run`, quebrando `AIRFLOW_HOME` — corrigido com
   `MSYS_NO_PATHCONV=1` no comando.
2. `pyarrow` sem versão fixada no `requirements.txt` resolveu para `19.0.0` no container, contra
   `25.0.1` no host que escreveu o parquet original — erro real na leitura
   (`OSError: Repetition level histogram size mismatch`, incompatibilidade de formato entre
   versões). Corrigido fixando `pyarrow==25.0.1` (mesma versão do host) no
   `airflow/requirements.txt`.

## Estratégia de testes

Sem teste automatizado (infraestrutura de orquestração, não código de aplicação — mesmo raciocínio
já usado pro `Dockerfile`/`docker-compose.yml`). Validação manual real via `airflow dags test`,
com output colado, e checagem do arquivo resultante no host.

## Riscos

- Container Airflow não persiste nada entre runs (sem volume nomeado pro metadata DB) — aceitável,
  o requisito é "rodou uma vez com sucesso", não "serviço Airflow rodando continuamente".
- Split/seed idênticos ao ML-003 (`random_state=42`, `test_size=0.2`, `class_weight="balanced"`) —
  o `.joblib` resultante deve ser equivalente ao já treinado; não há necessidade de recomparar
  métricas porque a lógica de treino é literalmente a mesma da ML-003, já validada.
- ~~Risco real encontrado, não corrigido por decisão de escopo/prazo~~ **Corrigido na sessão
  seguinte, antes do OPT-001** (não ficou pendente): o container do Airflow instalou
  `scikit-learn==1.9.1` (sem versão fixada em `requirements.txt`), enquanto a API
  (`pyproject.toml`/`uv.lock`) estava em `1.9.0` — o `.joblib` gerado pela DAG carregava
  corretamente na API mesmo assim (`InconsistentVersionWarning`, não erro), mas era drift de
  ambiente real entre quem treina e quem serve. Fixado `scikit-learn==1.9.0` nos dois lugares
  (`pyproject.toml` e `airflow/requirements.txt`), container reconstruído e baseline retreinado
  via a própria DAG — `.joblib` resultante carrega sem warning de versão. Ver
  [docs/specs/OPT-001.md](OPT-001.md), que dependia dessa correção antes da conversão ONNX.

## Re-validação pré-vídeo: instruções não subiam de verdade (achado real, não hipotético)

O usuário tentou seguir as instruções desta spec/README e não conseguiu subir o ambiente. Refeito
do zero, seguindo só o que estava escrito, sem usar conhecimento prévio de já ter feito isso antes.

### O que estava errado, especificamente

1. **O bloco de comando era só bash, apresentado como se funcionasse em qualquer shell.** O
   README chegava a dizer "irrelevante em Linux/macOS ou PowerShell" — **falso**: colar o bloco
   literal (continuação com `\`, `$(...)`) no PowerShell quebra completamente. Testado de
   verdade: `docker run --rm` roda sem nenhum argumento (`invalid reference format`), `-e`/`-v`
   viram tentativas de cmdlet inexistente, `air001-airflow` também. PowerShell não é "bash com
   sintaxe um pouco diferente" — não tem continuação de linha com `\`, e `$(...)` é avaliado pelo
   PowerShell, não repassado pro processo bash de dentro do container.
2. **`$(date +%F)` é bash puro.** Em PowerShell, `date` é alias de `Get-Date`, e `+%F` não é um
   parâmetro válido — gera `Get-Date : Não é possível associar o parâmetro 'Date'...`, um erro
   feio que parece (mas não é, nesse caso específico) fatal.
3. **Nunca ficou explícito que os comandos precisam rodar a partir da raiz do repositório.**
   Implícito pelo `./airflow` e `$(pwd)`, nunca dito. Alguém que navegou pra dentro de `airflow/`
   primeiro (razoável, é o diretório sendo referenciado) receberia erro de arquivo não encontrado.
4. **Achado mais sério, encontrado só porque o script de validação checa o resultado, não só o
   código de saída**: se a data de execução passada pra `airflow dags test` for **anterior** ao
   `start_date` da DAG (`datetime(2026, 1, 1)`, em `airflow/dags/air001_train_baseline.py`), o
   Airflow marca a `DagRun` como `state=success`, com exit code `0`, **sem executar nenhuma
   task**. Não há warning, não há erro — é um sucesso vazio. Isso quase entrou na correção deste
   card: a primeira tentativa de simplificar o comando (pra fugir do problema #1/#2 usando uma
   data fixa) usou `2024-01-01` como "qualquer data serve, é só um identificador" — que é
   anterior ao `start_date` de 2026, e a run "passou" sem treinar nada. Só foi pego porque o
   script de validação (abaixo) confirma que o `.joblib` foi *atualizado* pela execução, não só
   que ele existe.
5. Não havia sinal claro de "deu certo" — uma parede de log do Airflow, sem indicação do que
   procurar. (`pyarrow`/`scikit-learn`, os dois problemas já documentados nas seções acima,
   continuam corrigidos — não reapareceram nesta re-validação.)

### Correção: scripts, não só documentação

`scripts/run_airflow_dag.sh` (Linux/macOS/Git Bash) e `scripts/run_airflow_dag.ps1` (PowerShell) —
cada um com a sintaxe nativa do seu shell, sem pedir pro usuário adaptar nada:

- Resolvem a raiz do repositório sozinhos (funcionam de qualquer diretório de partida) — corrige
  o achado #3.
- Usam a data de hoje, calculada nativamente em cada shell (`date +%F` / `Get-Date -Format
  yyyy-MM-dd`) — nunca fixa, sempre posterior ao `start_date` — corrige o achado #4 de raiz, sem
  precisar lembrar a regra toda vez.
- **Não confiam só no exit code do `docker run`** para dizer "deu certo": guardam um marcador de
  tempo antes de rodar e, no final, confirmam que `models/tfidf_logreg_baseline.joblib` foi
  **modificado depois** desse marcador — não só que existe (existir sozinho não prova nada se já
  havia uma run anterior bem-sucedida). Foi exatamente essa checagem que expôs o achado #4.
- Terminam com uma linha objetiva (`Tudo certo.` ou uma mensagem de erro específica), não uma
  parede de log pra interpretar.

**Validado de verdade, do zero, sem modelo presente, nos dois shells**:

$ bash scripts/run_airflow_dag.sh

Achado colateral também real, ao escrever o `.ps1` pela primeira vez (não sobreviveu à versão
final, mas vale registrar): usar `2>&1` num comando nativo (`docker run`) dentro do PowerShell
5.1 embrulha cada linha de stderr num `NativeCommandError` e aborta o script com
`$ErrorActionPreference = "Stop"`, mesmo quando o comando termina com exit code `0` — corrigido
não redirecionando stderr do `docker run` (a saída aparece direto no console, sem prejuízo).

## Script de demonstração visual (`run_airflow_ui.sh`/`.ps1`)

`run_airflow_dag.sh`/`.ps1` provam que a DAG funciona (`airflow dags test`) — não sobem UI
nenhuma, o container é `--rm` e sai sozinho ao terminar. Pro vídeo, era preciso algo que
ficasse de pé com a UI navegável. Em vez de misturar isso no script de teste (que continua
intocado, é o que prova o requisito), criei um par de scripts novo e separado:
`scripts/run_airflow_ui.sh` / `scripts/run_airflow_ui.ps1` — mesma imagem `air001-airflow`, mesmos
volumes/variáveis de ambiente do script de teste, porta `8080:8080` mapeada, rodando
`airflow standalone` em foreground (fica de pé até `Ctrl+C`, não é modo de produção — o próprio
Airflow avisa isso no log).

**Validado de verdade, nos dois shells**:

```
$ ./scripts/run_airflow_ui.sh
[...]
$ curl http://localhost:8080/health
{"metadatabase":{"status":"healthy"},"scheduler":{"status":"healthy"},"triggerer":{"status":"healthy"},...}
$ curl -o /dev/null -w "%{http_code}\n" http://localhost:8080/login/
200
$ docker exec air001-ui-standalone airflow dags list
dag_id                 | fileloc                                                     | is_paused
air001_train_baseline  | /opt/airflow/project/airflow/dags/air001_train_baseline.py | True
```

Confirmado nos dois shells (bash e PowerShell), subiu em ~18s cada vez.

**Onde fica a senha do `admin` — checado rodando de verdade, não assumido**: gerada
automaticamente pelo `airflow standalone` em `/opt/airflow/standalone_admin_password.txt`
*dentro do container*. O enunciado da tarefa levantou a hipótese de também aparecer no log de
inicialização — **testei e não aconteceu**: o webserver já estava respondendo tráfego real
(`/health`, `/login/` retornando 200) e o log não continha nenhuma linha `Login with username:
admin  password: ...` até esse ponto. O método confirmado é ler o arquivo, de outro terminal,
enquanto o container está rodando:

```bash
docker exec air001-ui-standalone cat /opt/airflow/standalone_admin_password.txt
```

**Trigger manual pela UI** (pro vídeo): a DAG aparece na lista mas `is_paused=True` por padrão
(comportamento default do Airflow, não um bug) — acessar `localhost:8080`, logar com
`admin`/a senha do arquivo, ativar o toggle ao lado de `air001_train_baseline`, clicar no nome
da DAG e no botão de play (▶, "Trigger DAG"), acompanhar a run na visão Grid.
